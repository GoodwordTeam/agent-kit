## 1. `protocols/invocation-authority.md`

**Contract:** states, once, which class of caller may start which class of operation, and what "authority" actually means when the file itself cannot enforce anything.

**Donor sources**

**Mechanisms to import**
1. **Two classes of operation, not one.** *Public entrypoints* (user-invoked skills) vs. *shared phase operations* (the model-invoked/internal mechanics a lifecycle skill delegates to, i.e. what lives under `protocols/phase-operations/`). A human can invoke a public entrypoint directly. A delegated controller (an autopilot supervisor pair, a lifecycle skill orchestrating its own phase) may invoke a phase operation **only when a runner-validated grant covers it** — plan §7.1 (L452).
2. **Ordinary workers cannot manufacture a grant.** An implementer or reviewer subagent cannot start a new gated phase, approve its own work, or promote itself to a class it wasn't dispatched as — this is the connective tissue between this file and every role file in the batch (`implementer`, `reviewer-spec`, `reviewer-standards`, `supervisor` all restate their piece of it).
3. **Respect native manual-only restrictions by stopping, not reproducing.** Where the host cannot support a separately authorized internal call, the correct behavior is to halt and ask for explicit invocation rather than achieving the same effect through an alternate ungated path — plan §7.1 (L454): *"Where that host cannot support a separately authorized internal operation, stop for explicit invocation rather than reproducing a forbidden command's effects through an alternate path."*
4. **Ship creates a lesson candidate; publishing still needs authorization.** plan §7.1 (L456): *"Ship can create a lesson candidate automatically, but publishing it requires either explicit authorization or a charter grant for KB publication. It must not treat 'ship happened' as permission to rewrite project knowledge."*
5. **Distinguish real fail-closed authority from advisory evidence.** This is the single most important donor lesson for this file and has no equivalent in the plan text itself — see Adapted passages.

## 2. `protocols/phase-operations/PROTOCOL.md`

**Contract:** defines the shared, model-invoked mechanics that public lifecycle entrypoints (and autopilot, once authorized) actually call — one definition per phase operation, each with owner, authority class, preconditions, postconditions, side effects, idempotency behavior, and a closed result-status vocabulary.

**Donor sources**
- `plan §4 (L214)` — directory comment: *"Shared implementations for manual/delegated calls."*
- `plan §7.4 (L480-490)` — the runtime state machine and result-status vocabulary.
- `plan §7.4 (L488)` — idempotency-key + read-back requirement for remote/side-effecting operations.
- `compound-engineering@05c42da94fd318fa081f29d17bf947762aa477b1:skills/ce-code-review/references/finish-review.md#L1` — the leaf/dispatch-context split, as a concrete example of "phase operation" granularity in an existing donor pipeline.
- `omc@5281b19e0d64f8e6dc6767f2130299a88af2dc71:skills/plan/SKILL.md` — the `state_write`/`state_clear` pattern around a stop-hook, as a worked example of "distinguish handoff-to-execution from true terminal exit" in phase-state management.

**Mechanisms to import**
1. **The plan's five-state result vocabulary is the return contract for every phase operation**, not just the top-level lifecycle: `plan §7.4 (L486)`: *"At any state, return one of `needs-input`, `cap-reached`, `failed`, or `cancelled`"* — the batch brief's brief additionally names `complete` as the success case, giving the closed set `complete | needs-input | cap-reached | failed | cancelled`. Every phase operation in the catalog must resolve to exactly one of these.
2. **Idempotency keys + read-back checks on every remote/side-effecting op.** `plan §7.4 (L488)`: *"Branch creation, pushing, posting comments, resolving threads, and PR creation use idempotency keys plus read-back checks."* Import as a hard requirement on the operation contract's "side effects" field: any phase operation whose side effect is externally visible (not just local-worktree) must declare its idempotency key derivation and what read-back proves the effect already happened before retrying.
3. **State transitions validate four things, in this order: prerequisites, evidence freshness, authority, budgets** — `plan §7.4 (L488)` implicitly, `plan §5.2 (L340-344)` explicitly for evidence freshness: *"Approvals bind to an artifact's hash or revision, not to its filename. A changed plan does not inherit the previous plan's approval. A changed patch does not inherit stale test receipts."* This is the precondition-checking mechanism every phase operation's "preconditions" field must be able to express.
4. **Concrete example of leaf-vs-dispatch-context granularity** (useful as a worked illustration for how to split a phase operation from its orchestration, not as an importable literal mechanism — the CE pipeline is a single skill's internal staging, not a cross-skill phase operation):
   > `finish-review.md#L1`: *"This reference runs across three contexts: a merge leaf runs Stage 5 and Stage 5b steps 1 through 3... the dispatch context runs Stage 5b step 4... a report leaf runs Stage 5b step 5... Each leaf reads `<run-dir>/finish-input.json` first."*
   Adaptation: this demonstrates naming *exactly* which context does which piece of work and what file each one reads first — a phase operation's "preconditions" and "inputs" fields should be this concrete (name the exact input artifact, not "relevant context").
5. **Distinguish "handoff to execution" from "true terminal exit."** The omc `plan`/`ralplan` skills manage a `ralplan-state.json` via `state_write`/`state_clear` wrapped around a stop-hook specifically so that finishing a planning phase and *handing off* to a build phase is not confused with the session actually ending. This is host-specific plumbing (a Claude Code stop-hook) but the underlying principle generalizes directly to `phase-operations`' result-status design: a phase operation that ends in `complete` because its own scope finished is not the same event as the *lifecycle* being done, and the protocol should say explicitly that a phase operation's `complete` result hands control to the next phase rather than terminating the run.

**Adapted passages**

Store the next permitted action and checkpoints so a restart does not repeat side effects. ... ## 3. `protocols/consensus-plan-gate/PROTOCOL.md`

**Contract:** planner snapshot → architect → critic → synthesis, on a single fixed artifact snapshot, architect and critic each working from that snapshot alone (never from each other's analysis), bounded at five rounds, producing one whole-plan verdict — invoked only for genuine architectural disagreement, high-risk planning, or a review-driven replan.

**Donor sources**
- `omc@5281b19e0d64f8e6dc6767f2130299a88af2dc71:skills/ralplan/SKILL.md` — primary mechanism source (read in full): 8-step workflow, RALPLAN-DR structured-deliberation summary format, the mandatory-sequential (never-parallel) Architect-then-Critic rule stated multiple times, the 5-iteration cap, ADR output requirement, the Planning/Execution Boundary ("no mutation before explicit approval"), and a Pre-Execution Gate section with a Good/Bad prompt-signal table.
- `omc@5281b19e0d64f8e6dc6767f2130299a88af2dc71:skills/plan/SKILL.md` — elaborates the same mechanics (`ralplan` is documented there as literally an alias for `plan --consensus`); also documents Interview/Direct/Review modes (not relevant to this protocol) and the state-lifecycle pattern already covered under `phase-operations`.
- `omx@cb955b0d5becbef76d2c1f0096b6e1f238e1e7f7:skills/ralplan/SKILL.md` — same Planner→Architect→Critic→synthesis mechanics, wrapped in host-authority/tracker language (mostly excluded); notably states a standalone `--advisory` run "never emit[s] a PreToolUse allow/block decision, never complete[s] the host consensus gate, never authorize[s] execution" — directly useful for this protocol's own authority boundary (an advisory/exploratory consensus run must not be confusable with an authorized plan-gate pass).
- `plan §2.5 (L146)`, `plan §6.5 (L440-442)`, `plan §11 (L647)`.
- Transcript: `G:L610-744` (doc-review vs. ralplan comparison), specifically `G:L698-704`.

**Mechanisms to import**
1. **Strict sequential ordering, never parallel — independence-from-contamination, not independence-from-shared-context.** This is the omc source's most emphatic, repeated rule: the critic must never see the architect's analysis before forming its own judgment, and the architect must never see the critic's. Contrast explicitly with the *different* independence pattern used in `review-delta`/two-lane review, where the two lanes run in parallel precisely because their independence comes from not sharing a review context at dispatch time, not from ordering. **Do not conflate these two mechanisms** — they solve different problems (sequential prevents anchoring on a peer's argument; parallel prevents anchoring on a shared session).
2. **Fixed snapshot.** Both architect and critic inspect the *same* artifact revision; a snapshot taken mid-analysis and mutated before the critic runs invalidates the run. `plan §6.5 (L440)`: *"Preserve architect-then-critic ordering on a fixed snapshot and a five-round limit. Independence comes from isolated evidence packets, not merely from sequential scheduling."*
3. **Bounded at five rounds.** `plan §6.5 (L440)` and `plan §2.5 (L146)` both state the cap; `plan §10` scenario 18 (L624) tests it directly: *"The third fix cycle stops"* is the apply-findings analog — for this protocol the release-scenario equivalent is "the sixth round never runs."
4. **Whole-plan verdict, not a finding bucket.** Contrast directly with `doc-review`'s output shape — this is the load-bearing distinction from the transcript comparison (see Adapted passages).
5. **Planning/Execution Boundary.** No mutation of the target repository before explicit human (or charter-granted) approval — this is the same boundary `invocation-authority.md` states generically; this protocol is one of its concrete instances.
6. **Narrow invocation trigger.** `plan §6.5 (L440)`: *"Invoke it for genuine architectural disagreement, high-risk planning, or a review-driven replan—not automatically on every bound invocation."* This is a hard scope boundary: `super-bound` does not run this protocol by default on every planning pass.

Output is an edited doc plus a decision list. No single verdict. Use ralplan when you need the plan to be allowed to die. 2. **Red-Green-Refactor with mandatory verification at each edge, not just at the end.** superpowers requires an explicit "Verify RED" step (watch the test actually fail, for the reason you expect, before writing implementation) and an explicit "Verify GREEN" step (watch it pass, for the reason you expect) — a green result achieved by accident (e.g. the test didn't actually exercise the new code path) is exactly the failure mode this catches. Do not collapse red/green into "write test, write code, run once."
3. **"Seams" — pre-agreed, user-confirmed public-interface test boundaries.** Pocock's distinctive contribution: before writing any test, the implementation-relevant public boundary ("the seam") is proposed and confirmed with the user, so tests are written against a stable, agreed contract rather than against whatever the implementer happens to expose first. This directly prevents Pocock's first named anti-pattern (implementation-coupled tests).
4. **Three named test anti-patterns (Pocock):** implementation-coupled (test breaks on refactor even though behavior didn't change), tautological (test restates the implementation rather than asserting behavior), horizontal-slicing (testing layer-by-layer instead of vertical-slice-by-vertical-slice; Pocock prefers vertical slices).
5. **"Discover the Stack First" (Addy).** Never assume `npm test` (or any specific command) — a TDD protocol that hardcodes a test runner will silently pass on a repository that uses a different one. Discover the actual verification command before applying the red/green discipline.
6. **"Prove-It Pattern" for bug fixes (Addy).** A bug fix's red step is specifically: write a test that reproduces the reported bug and watch it fail *for the reported reason* before writing the fix. This is TDD's bug-fix-specific instance and should be named explicitly, since `super-build`/`diagnose` both need it.
7. **Non-testable work needs a recorded alternative verification plan, not a silent exemption.** This exact phrase is the batch brief's own framing (not a direct donor quote) but is fully supported by the donor material's spirit: superpowers' "When Stuck" table and Addy's Verification checklist both assume *some* verification artifact always exists; neither donor contemplates "no verification, no explanation." Import as an explicit protocol requirement: if the change genuinely cannot be red/green tested, the protocol requires naming what verification *was* done instead (a probe, a manual reproduction, an inspection) rather than allowing the step to be silently skipped.
8. **Mocking discipline (Pocock).** Mock only at system/service boundaries (network, filesystem, external SDK), never at internal module boundaries; prefer dependency injection and typed SDK interfaces over patching internals.
9. **Mock-preference order (Addy):** Real > Fake > Stub > Mock, applied in that order of preference — only fall back to a heavier-weight double when a lighter one is unavailable.
10. **Anti-rationalization tables are load-bearing content, not filler.** Both superpowers (10 rows) and Addy (a similarly-shaped table) exist specifically because agents talk themselves out of the discipline under time pressure ("tests are slow," "this is just a spike," "I'll refactor after," "it's obviously correct"). Import the *mechanism* (a table pairing a common rationalization with its rebuttal) even where the exact rows are rewritten for this repository's voice.
